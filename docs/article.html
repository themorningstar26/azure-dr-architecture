What I learned

It's 3 AM. Your primary region goes down.

Your phone blows up. Customers are tweeting. Your SLA clock is ticking.

Your on-call engineer scrambles to login. They try to SSH into failing servers. The runbook is 40 steps long. Half the steps assume things that no longer exist.

Now imagine a different scenario.

"Failover complete. No action needed."

Your app detected the failure at T=0. By T=90 seconds, traffic was already flowing through your DR region in West Europe. Your database was promoted. Your pods were scaled. Your app was serving customers.

Your phone rang — but only to inform you, not to wake you up and make you fix something.

That's what I built. Here's exactly how.

Critical: The entire DR system depends on one piece of code your team writes. If you get this wrong, Front Door will never trigger failover — even when your app is completely broken.
The wrong way — DR never triggers
// ❌ WRONG — always returns 200, even when DB is down
app.get('/health', (req, res) => {
  res.status(200).json({ status: 'healthy' });
  // Front Door sees 200 → thinks all is fine → DR never triggers
  // Your app is dead but Front Door doesn't know
});
javascript
The right way — Node.js / Express
// ✅ CORRECT — tests real dependencies
app.get('/health', async (req, res) => {
  try {
    await db.query('SELECT 1');        // real DB check
    await redis.ping();                // real cache check
    res.status(200).json({
      status: 'healthy',
      region: process.env.REGION     // "eastus" or "westeurope"
    });
  } catch (err) {
    res.status(503).json({            // 503 → Front Door triggers failover
      status: 'unhealthy',
      error: err.message
    });
  }
});
javascript
Same logic — Python (Flask / FastAPI)
# ✅ Python version — same concept
@app.route('/health')
def health():
    try:
        db.execute('SELECT 1')
        redis_client.ping()
        return jsonify({"status":"healthy","region":os.getenv("REGION")}), 200
    except Exception as e:
        return jsonify({"status":"unhealthy","error":str(e)}), 503

Kubernetes liveness + readiness probes — link to AKS
# k8s/base/frontend-deploy.yaml
livenessProbe:
  httpGet:
    path: /health
    port: 8080
  initialDelaySeconds: 15
  periodSeconds: 20
  failureThreshold: 3   # 3 failures → pod restarted

readinessProbe:
  httpGet:
    path: /health
    port: 8080
  initialDelaySeconds: 5
  periodSeconds: 10    # 10s check — faster than Front Door's 30s
yaml
Rule: /health must return 503 when the DB is unreachable, when Redis is down, or when any critical dependency fails. If it returns 200 in any of those cases — your DR system is theater.
Two completely separate paths: planned deploys go through CI/CD with approval gates. Emergency failover bypasses CI/CD entirely — it uses Azure-native automation that runs independently of any pipeline.

SQL Failover Group — Terraform (key resource)
resource "azurerm_sql_failover_group" "main" {
  name                = "fog-myapp"
  resource_group_name = var.primary_rg
  server_name         = module.sql.server_name
  databases           = [module.sql.database_id]

  partner_servers {
    id = var.dr_sql_server_id
  }
  read_write_endpoint_failover_policy {
    mode          = "Automatic"
    grace_minutes = 1    # 1 min heartbeat loss → auto-promote DR
  }
}

Create Automation Account + Managed Identity (Terraform)
resource "azurerm_automation_account" "dr" {
  name                = "aa-myapp-dr-failover"
  resource_group_name = var.primary_rg
  sku_name            = "Basic"

  identity {
    type = "SystemAssigned"   # Managed Identity — zero passwords
  }
}

resource "azurerm_role_assignment" "runbook_dr" {
  scope                = "/subscriptions/${var.sub_id}/resourceGroups/${var.dr_rg}"
  role_definition_name = "Contributor"
  principal_id         = azurerm_automation_account.dr.identity[0].principal_id
  # Only DR resource group — not entire subscription
}
hcl
Critical: The Runbook uses az login --identity inside the script. No clientSecret ever appears in code, pipeline YAML, or git. The Managed Identity is the credential — managed entirely by Azure and Terraform.
Failover is 100% automatic. Failback is intentionally manual. During the failover window, your DR database was accepting writes. Those writes must replicate back to primary before you switch back. Automated failback risks data loss.
Why failback must be human-triggered
Risk without verification
Stale data
Primary restarts with data from before the outage. DR writes are lost.
Safe failback window
2–5 minutes
Time needed for SQL to replicate DR writes back to primary.
Failback pipeline — manual trigger, approval gate
# Step 1: Verify primary is stable (10 checks over 5 minutes)
for i in {1..10}; do
  CODE=$(curl -s -o /dev/null -w "%{http_code}" \
    https://app-primary.eastus.azurecontainer.io/health)
  if [ "$CODE" != "200" ]; then exit 1; fi
  sleep 30
done

# Step 2: Re-enable primary in Front Door (it auto-recovers when healthy)
az afd origin update --enabled-state Enabled ...

# Step 3: Wait for SQL replication DR → Primary to sync
sleep 120

# Step 4: Failback SQL to original primary
az sql failover-group set-primary \
  --name fog-myapp \
  --resource-group rg-myapp-primary \
  --server sql-myapp-primary

# Step 5: Scale DR back to warm standby
az aks scale --resource-group rg-myapp-dr \
  --name aks-myapp-dr --node-count 2
bash
Front Door automatically routes back to primary (priority=1 is always preferred over priority=2) as soon as primary health probes pass again. You just need to fix the DB and scale DR back down.
3 things I wish I knew before building this
!
Untested DR = no DR
The architecture means nothing until you've run the drill. Disable the primary backend in Front Door. Watch /health flip from "eastus" to "westeurope". Measure the time. That number is your real RTO. Do this quarterly.
# Drill command — no real outage
az afd origin update --enabled-state Disabled ...
watch -n5 'curl -s https://app.company.com/health | python3 -c "import sys,json; print(json.load(sys.stdin)[\"region\"])"'
bash
!
The connection string is a hidden dependency
If your app connects to sql-primary.eastus.database.windows.net — the SQL failover group promotes DR perfectly, but your app still tries to hit a dead server. Always use the virtual failover group endpoint. Always.
WRONG: sql-myapp-primary.eastus.database.windows.net
RIGHT:  fog-myapp.database.windows.net
config
✓
Warm standby costs less than you think
Running DR at 2 nodes (vs 0) adds ~30% infra cost but cuts failover time from 10–30 minutes (cold start) to under 2 minutes. For production workloads with any SLA, that's an easy trade. The interview question is "what's your RTO?" not "what's your cost?"
Cold DR (0 nodes)
10–30 min RTO
Cheaper. Unacceptable for most SLAs.
Warm standby (2 nodes)
<2 min RTO
~30% more cost. Production-grade.
